Desafio Backend Motor Rent

Relatório Completo de Arquitetura, Funcionalidades, Microsserviços e Guia Operacional

Sumário do Sistema

Este relatório técnico apresenta detalhadamente a engenharia, arquitetura e funcionamento do ecossistema construído para o desafio de gestão de frota de motos, motoristas entregadores, locações e gerenciamento de entregas. O sistema adota os princípios de Domain-Driven Design (DDD) e Clean Architecture, fundamentado na plataforma .NET 8, mensageria distribuída com RabbitMQ (MassTransit), persistência relacional com PostgreSQL 16 e orquestração de containers com Docker Compose.

Plataforma & Framework .NET 8 LTS (C# 12) / ASP.NET Core
Orquestração & Infra Docker Compose / Alpine Linux
Banco & Mensageria PostgreSQL 16 / RabbitMQ 3
Data da Emissão Novembro / 2026

1. Visão Geral da Solução e Arquitetura

A solução foi projetada sob o paradigma de Domain-Driven Design (DDD) e Clean Architecture (Arquitetura Limpa), estabelecendo limites arquiteturais claros, isolamento de responsabilidades e desacoplamento absoluto do núcleo de negócios em relação a frameworks, drivers e infraestrutura.

API REST DesafioBackend.Api (Porta 5000)

Ponto de entrada HTTP RESTful conforme contrato OpenAPI/Swagger. Provê autenticação JWT Bearer, tratamento global de exceções, upload de documentos e injeção de dependências.

Web MVC DesafioBackend.Web (Porta 5001)

Portal Administrativo em ASP.NET Core MVC. Permite gestão visual de motos, entregadores, locações com simulação de taxas e controle em tempo real de pedidos disponíveis, em trânsito e concluídos.

Mensageria RabbitMQ + MassTransit (Porta 5672 / 15672)

Broker orientado a eventos assíncronos. Processa eventos de domínio como MotorcycleRegisteredEvent, filtrando motos do ano 2024 para auditoria e notificações reativas.

Persistência PostgreSQL 16 (Porta 5433 / 5432)

Banco relacional com transações atômicas ACID, índices únicos de negócio (CNPJ, CNH, Placa), migrações automáticas via EF Core e volume persistente para segurança dos dados.

Toda a stack de microsserviços e dependências é orquestrada através do arquivo docker-compose.yml, permitindo que a aplicação seja inicializada do zero com um único comando, sem necessidade de configuração prévia de bancos de dados ou servidores na máquina hospedeira.

Configuração do Dockerfile Multi-Stage

Tanto a API quanto o projeto Web utilizam Dockerfiles multi-stage baseados na imagem oficial mcr.microsoft.com/dotnet/sdk:8.0 para compilação e mcr.microsoft.com/dotnet/aspnet:8.0-alpine para execução em produção. Isso garante:

  • Tamanho reduzido de imagem (menos de 220 MB por container).
  • Superfície de ataque mínima por utilizar o kernel Alpine Linux endurecido.
  • Separação total entre ferramentas de build (SDK, compiladores) e o runtime final.

3. Mensageria Assíncrona e Arquitetura Orientada a Eventos (RabbitMQ)

O sistema adota mensageria para desacoplar operações de cadastro de frotas e processamento reativo. A comunicação com o broker RabbitMQ é abstraída através do MassTransit, framework padrão da indústria que provê resiliência, reconnect automático e tópicos baseados em tipos de eventos.

Detalhamento do Produtor e Consumidor

1. Produtor (Producer - MotorcycleService)

Ao receber uma requisição de cadastro de moto válida, o serviço de aplicação persiste o registro e dispara o evento assíncrono:

await _messageBus.PublishAsync(
    new MotorcycleRegisteredEvent(motorcycle.Id, motorcycle.Year, motorcycle.Model, motorcycle.Plate), 
    cancellationToken);

2. Consumidor (Consumer - MotorcycleCreatedConsumer)

O consumidor escuta a fila dedicada e implementa a regra de negócio do desafio técnico: quando o ano de fabricação da moto for 2024, uma notificação especial deve ser gerada e persistida:

public async Task Consume(ConsumeContext<MotorcycleRegisteredEvent> context)
{
    var message = context.Message;
    if (message.Year == 2024)
    {
        var notification = new MotorcycleNotification(
            id: Guid.NewGuid().ToString(),
            motorcycleId: message.MotorcycleId,
            year: message.Year,
            model: message.Model,
            plate: message.Plate,
            message: $"Moto ano 2024 cadastrada com sucesso com a placa {message.Plate}."
        );
        await _notificationRepository.AddAsync(notification, context.CancellationToken);
        await _unitOfWork.CommitAsync(context.CancellationToken);
    }
}
Auditoria no Painel do RabbitMQ: O administrador pode acompanhar as filas ativas, taxas de entrega e mensagens em trânsito através do painel oficial em http://localhost:15672 (usuário: guest, senha: guest).

4. Especificação das Funcionalidades de Negócio

4.1. Gestão de Frotas de Motos

  • Cadastro de Moto: Requer identificador único, ano, modelo e placa única. Caso a placa ou identificador já existam, a API retorna erro 400.
  • Consulta e Filtro por Placa: Permite consultar todas as motos ou filtrar via query string GET /motos?placa=XYZ.
  • Atualização de Placa: Endpoint PUT /motos/{id}/placa permite modificar exclusivamente a placa, garantindo que a nova placa não colida com outra moto existente.
  • Exclusão de Moto: Endpoint DELETE /motos/{id}. Valida integridade referencial: caso a moto possua qualquer registro histórico de locação vinculado, a exclusão é rejeitada com erro 400.

4.2. Gestão de Motoristas Entregadores

  • Cadastro com Unicidade: Validação obrigatória de unicidade de CNPJ e numero_cnh em nível de aplicação e banco de dados (índices únicos).
  • Categorias de CNH Aceitas: Suporta categorias A, B e A+B.
  • Upload de Imagem da CNH: Endpoint POST /entregadores/{id}/cnh recebe a imagem em formato multipart/form-data. O serviço valida formatos permitidos (.png e .bmp) e salva o arquivo em diretório seguro configurado, atualizando a URL no perfil do entregador.

4.3. Gestão de Locação de Motos e Regras Financeiras

O módulo de locações implementa as regras rigorosas de elegibilidade e tarifas contratuais:

Regra de Habilitação: Apenas entregadores habilitados na categoria A (ou A+B) têm permissão para alugar motos. Entregadores que possuem apenas categoria B são bloqueados.

Regra de Atraso na Devolução: Caso a moto seja devolvida após a data prevista de término, é cobrado o valor total base do plano contratado acrescido de uma tarifa fixa de R$ 50,00 por diária adicional excedente.

Início Obrigatório da Locação: A data de início da locação deve ser obrigatoriamente o primeiro dia útil seguinte à data de criação (D + 1).

4.4. Gestão de Pedidos e Entregas

  • Criação de Pedidos: Pedidos com descrição e identificador são disponibilizados na plataforma com status Available.
  • Vinculação e Aceite: Um entregador só pode aceitar uma entrega se tiver uma locação ativa no momento. O status passa para Accepted.
  • Conclusão da Entrega: Apenas o motorista vinculado ao pedido tem permissão para marcar a entrega como Completed.

6. Segurança, Autenticação e Documentação OpenAPI / Swagger

Mecanismo de Autenticação JWT Bearer

A API implementa autenticação baseada em tokens JSON Web Token (JWT) assinados com algoritmo HMAC-SHA256.

  • Endpoint de Login: POST /auth/login recebe usuário e senha (padrão: admin / admin) e retorna o token com tempo de expiração e claims de permissão.
  • Proteção de Endpoints: As rotas de negócio exigem o cabeçalho Authorization: Bearer <token>, garantindo que requisições não autorizadas sejam rejeitadas com status 401 Unauthorized.

Configuração do Swagger com Suporte a Bearer Token

A interface do Swagger em http://localhost:5000 está equipada com o recurso AddSecurityDefinition("Bearer", ...):

  1. Ao acessar a documentação interativa, clique no botão Authorize (ícone de cadeado verde no topo).
  2. Insira o token obtido no endpoint de autenticação no formato: Bearer <seu_token>.
  3. A partir deste momento, todas as requisições disparadas pelo Swagger incluirão automaticamente o token de autorização.

Procedimentos de Depuração no Visual Studio 2022

Opção A: Depuração Local com Dependências no Docker (Recomendada)

  1. Inicie apenas o PostgreSQL e o RabbitMQ em background: 
    docker compose up -d db rabbitmq
  2. Abra a solução DesafioBackend.sln no Visual Studio 2022.
  3. Configure inicialização múltipla: clique com botão direito na solução → Configurar Projetos de Inicialização... → Marque Iniciar para DesafioBackend.Api e DesafioBackend.Web.
  4. Pressione F5 para iniciar com breakpoints e Hot Reload ativos.

Opção B: Anexar o Depurador ao Processo dentro do Container Docker

  1. Suba a stack inteira no terminal: docker compose up -d
  2. No Visual Studio, pressione Ctrl + Alt + P (Depurar → Anexar ao Processo...).
  3. Em Tipo de Conexão, escolha Docker (Contêiner do Linux).
  4. Selecione o container desafio_backend_api ou desafio_backend_web e anexe ao processo dotnet.
